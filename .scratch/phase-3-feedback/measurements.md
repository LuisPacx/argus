# Phase 3 slice 1: measurements (ticket 01)

Measured 2026-11-08. Method: a random sample of PumpPortal migrate Signals stored by argus from 2026-11-07T14:18Z to 2026-11-08T17:17Z (read-only copy of the live DB), then for each mint two Helius Free calls (`getTransactionsForAddress`): the mint's first successful transaction (the `CreateV2` transaction, which carries the `CreateEvent` with the metadata uri and the bonding-curve address) and the last transactions on the bonding curve (the `Migrate`/`MigrateV2` transaction and the `CompleteEvent`). Chain times are Solana `blockTime` (whole seconds). Plus a 9-minute live capture of the PumpPortal stream (77 creates, 2 migrates, 2026-11-08 17:59-18:08Z). The scripts were throwaway and are not committed (they hold RPC calls, which `adr-0002.test.ts` bans in source); the recorded responses are in `packages/core/src/fixtures/`.

Sample: 140 mints drawn; 117 usable. Dropped: 5 are not on the pump program (no bonding curve; see "PumpPortal migrate scope"), 5 repeats, 13 where the Migrate transaction was not among the curve's last 6 transactions (not investigated). Margin of error for a share at n=117 is about plus or minus 9 points. Everything below is one 27-hour window (a Saturday-Sunday), so it is a snapshot, not a seasonal average.

## Answers per spec section 14 item

**1. Snapshot age and Fast threshold.** Create to migrate (chain event times, n=117): 34% migrate in the same second (all 40 same-slot cases: create, buy-out and migrate land in one slot, a bundle); 39% within 60 s; 50% within 120 s; 58% within 180 s; 71% within 300 s; 78% within 10 min; 86% within 30 min; 88% within 1 h; 91% within 24 h. Percentiles read off those shares: p25 0 s, p50 about 120 s, p75 about 450 s, p90 about a day (9% migrate more than a day after creation, the longest 62 days).
- The 30-minute starting value does not work: it would flag 86% of migrators as Fast and leave 14% for Rubric lessons. The 3-minute starting Snapshot age also does not work: 58% of migrators are already migrated by then, so the Snapshot would be taken after the event for most.
- Proposed: metadata and website Snapshot at 60 s after create (metadata is immutable once the uri is set; the uri is already in the create payload), X at 5 min (window 5-15 min). **Fast = migrated at or before the website Snapshot age = 60 s** (39% of migrators, of which 34 points are same-slot bundles; both are excluded from Rubric lessons, which leaves 61% to learn from). X at 5 min leaves 29% of migrators to be pre-migration. If the Operator wants more room, 120 s moves Fast to 50%.
- Create to complete (curve full, n=94 where the `CompleteEvent` was found): p10 0, p25 79 s, p50 186 s, p75 658 s (the 28 migrators without a found `CompleteEvent` are mostly same-slot bundles, so this is slower than the table above).
- Complete to pool: p50 0 s, p90 1 s, max 1 s (same second or the next). Pool creation is the `Migrate` transaction itself (the `CreatePool` event is emitted inside it).

**2. Migrated timestamp.** Use the `Migrate`/`MigrateV2` transaction time (pool creation, the glossary sense). It trails curve complete by at most 1 s in the sample (n=94), so the choice barely changes any number; pool creation is what the PumpPortal `migrate` event reports and is the one that matches "moved to a swap pool". Store both anyway (spec section 6).

**3. PumpPortal receipt time vs chain.** `published_at` is real receipt time, not a poll batch time: migrate receipt minus chain `blockTime` has median about 0.7 s, p90 1.3 s, max 1.8 s with one 15.8 s outlier (n about 117; chain time is truncated to the second, so 0-1 s is rounding). Create receipt minus chain create time (n=52): 0.2-1.2 s. So the stored `published_at` can serve as the event time to about 1 s for both create and migrate; the cos note "possibly the poll batch time" is refuted. Labels at 24 h and 7 d need no better.

**4. PumpPortal migrate scope.** Not only pump-to-pumpswap. Of 1,313 stored migrate Signals, 84 (6.4%) have a mint that does not end in `pump`; 5 sampled ones had no pump-program bonding curve at all (the create transaction is not a pump create). PumpPortal's create stream also carries other launchpads (`pool: "bonk"`, LetsBonk, mints ending `...Loat`: 306 of 20.6k stored creates, 4 of 77 captured; those bonk creates carry no `uri`). The two captured migrate payloads were both `pool: "pump-amm"`; a migrate payload for another launchpad was not captured (so its `pool` value is unverified). The adapter stores neither `pool` nor `uri` today. Ticket 03 and 04 should keep the payload `pool` and restrict Cases to pump mints; the unfiltered feed mixes in about 6% non-pump migrations.

**5. Metadata uri source.** The PumpPortal create payload carries `uri` for pump creates (73 of 73 captured pump creates; 0 of 4 bonk creates). 96 of 122 uris are `ipfs.io/ipfs/...`; the rest are Vercel blob and `meta.uxento.io`. Cost: 0 Helius credits. The cos note "PumpPortal does not store the uri" is true only of the adapter (`pumpportal.ts` drops it), not of the feed. On-chain fallback (the `CreateEvent` in the create transaction, verified to carry the same uri) costs 10 credits per create. Ticket 02 should keep `uri` from the payload.

**6. Helius Free.** `getTransactionsForAddress` is allowed on Free (HTTP 200 for signatures-only, full, ascending, descending, filters on `status` and `blockTime`, `paginationToken`). Gotchas: full transactions need `maxSupportedTransactionVersion: 1` (some creates are version-1 transactions; 0 fails with error -32015); a bad address or version error returned an error and (per the docs) costs 0. No 429 at sequential calls of roughly 5-10 per second. Credit costs are from the Helius docs (https://www.helius.dev/docs/billing/credits); the response carries no credit header, and no usage endpoint is reachable with the key, so they are not independently measured: `getSignaturesForAddress`, `getTransaction`, `getMultipleAccounts` 1 credit; `getTransactionsForAddress` 10 flat for signatures (up to 1,000 per page), 10 per 100 full transactions with a 10-credit minimum; 0 on a failed response.
- Per Case: uri 0; chain create and migrate times for one migrator 20 (two calls; mostly avoidable, since PumpPortal receipt is within about 1 s of chain: needed only for creates PumpPortal missed, 10 each); a label read at 24 h or 7 d: 0.01 per Case (100 curve accounts per `getMultipleAccounts`, 1 credit; the account layout has the `complete` flag at byte 48, recorded in `helius-multiple-accounts.json`); wallet analysis for the bot filter (full transactions of the curve): curve sizes were 293, 4, 400, 262, 5, 472, 3,793+, 314, 729, 5, 393, 1,121, 636, 312, 5 successful transactions (median 314), so about 40 credits at the median, about 60-100 on average with the heavy tail.
- Budget: the feed delivers about 34 migrations per hour of uptime (about 800 a day). Reading the create plus a full curve for every migrator would cost 20 + 60-100 credits each, about 65k-100k credits a day, 2-3M a month: over the 1M Free budget. Restricted to the population (migrators with a website or X link, a share not yet measured; assume 30-50%) the same work is 0.7-1.5M a month, so it is borderline. Labelling alone (0.02 per Case) and times from PumpPortal receipts are negligible. Recommendation: Free is enough for 3a labelling; ticket 04's wallet analysis must carry a daily credit cap and a page limit per curve (for example the first 300 transactions), and the War Room credit counter decides when to ask for the $49 plan. This spike used 420 Helius calls, at most about 4,200 credits (0.4% of a month; fewer in fact, since 63 calls failed free).

**7. RugCheck.** Terms: not confirmed. The terms page is a client-rendered app that could not be read without a browser, and no API terms page was reachable, so no ToS clause could be quoted. Rate limit: the API (`https://api.rugcheck.xyz/v1/tokens/{mint}/report/summary`, no key, HTTP 200) answers with `x-rate-limit-limit: 15` and `x-rate-limit-remaining: 14` after one call; the window length is not in the headers and was not probed (one call made). **Sixth signal: no, until the Operator has read the terms** (spec section 8 includes it only once the ToS is confirmed). The signal costs nothing else to add later.

**8. Missed-create rate.** Of the 117 sampled migrates, 68 (58%) have no create Signal in argus. Split: 0 of 68 fall in the 11-07 04:00-13:00Z lid-suspend outage (the sample starts after it, and a token created in the outage that migrated later would have shown up as an old create; none did); 11 were created before argus's first capture (11-06 18:28Z); the remaining 57 (49% of all migrates) are unexplained. Argus is not the cause: a parallel client on the same PumpPortal stream received 77 creates in 9 minutes and argus stored 76 of the same 77 in the same period (the odd one out most likely a poll boundary), and the stored create rate (about 600 per hour) matches the live rate (about 510 per hour). So PumpPortal's `subscribeNewToken` does not deliver a create event for about half of the tokens that later migrate, typically tokens that migrate 1-4 minutes after create (the unexplained rows have create-to-migrate p50 about 180 s), while tokens that migrate in the same slot as the create do have a create row (30 of 40, 75%). Consequence: create time must come from the chain (10 credits per Case) when no create Signal exists, and Case selection cannot assume a create row; the population for the Snapshot (spec section 6: capture at creation) is the creates the feed does deliver, which under-represents migrators by about half. Whether PumpPortal drops them or sends them under another event is not known.

## Other findings

- Bundles: 34% of sampled migrators go from create to pumpswap pool inside one slot (create, buys that fill the curve, `Migrate`). These are bot-driven by construction; the bot filter (ticket 04) should flag same-slot bundles directly, and they overlap with Fast.
- Empty-app-shell share and Playwright headless vs headed: not part of this ticket.
