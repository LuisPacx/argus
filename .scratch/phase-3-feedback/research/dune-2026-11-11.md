# Dune as a data source for the migrated-token Study (2026-11-11, read-only)

Researched 2026-11-11 with WebFetch against primary pages only (Dune dashboard, docs.dune.com, dune.com/pricing, dune.com/terms) plus this repo. Nothing was run against the Dune API (no key). "Not verified" marks anything I could not read from the page that owns it. Terms follow `GLOSSARY.md`.

## Recommendation

Do not build a Dune pipeline. Dune's free tier is view-only (no API), the Operator's query is not what was assumed, and its SQL is unreadable without a browser. Dune is worth a one-off paid pull (trial or one Analyst month) only for months of history and a coverage cross-check; the forward spine stays PumpPortal plus chain reads (Phase 3 ticket 03). This agrees with the earlier verdict in `data-sources.md` (Dune row: "No for pipeline; maybe one-off").

## 2. Programmatic access

- Base URL `https://api.dune.com/api/v1`; key in header `X-DUNE-API-KEY` (or `api_key` query param); keys are per user or team, scopes Read or Read/Write ([authentication](https://docs.dune.com/api-reference/overview/authentication)).
- Fetch latest results: `GET /query/{query_id}/results`, Read scope, no new execution but it spends credits by result size. Params `limit`, `offset` (pagination; response carries `next_offset` and `next_uri`), `columns` (fewer columns cost fewer credits), `filters`, `sort_by`, `sample_count`. Query must be public or yours. Latest results only come back if an execution matches the query's current SQL, otherwise 404 ([get results](https://docs.dune.com/api-reference/executions/endpoint/get-query-result)).
- Execute: `POST /query/{query_id}/execute`, Read scope, `performance` small/medium/large; cost is "based on actual compute resources used" (no published formula); 402 when over the billing-cycle limit, 403 if archived/unsaved ([execute](https://docs.dune.com/api-reference/executions/endpoint/execute-query)).
- Free tier: no API. "Free access is view-only; API usage requires an active trial or a paid plan" ([rate limits](https://docs.dune.com/api-reference/overview/rate-limits)). Free plan credits: 0 ([credit system](https://docs.dune.com/learning/how-tos/credit-system)). Trial: 2,500 credits for up to 7 days with Plus features, card required with a hold ([pricing](https://dune.com/pricing)). Analyst 4,000 credits/month at $1.875 per 100 (about $75); Plus 25,000 at $1.596 per 100 (about $399) ([credit system](https://docs.dune.com/learning/how-tos/credit-system)). Dune's credit page gives no per-row or per-call credit rate, so the cost of a call is not verified.
- Rate limits (paid): Plus 70 rpm low-limit / 200 rpm high-limit endpoints; Enterprise 350+/1000+; 1000 req/s per IP; Analyst's number is not on the page ([rate limits](https://docs.dune.com/api-reference/overview/rate-limits)). Over-limit means throttling ([pricing](https://dune.com/pricing)).
- Terms ([terms](https://dune.com/terms)): Acceptable Use forbids "bots, crawlers, scrapers, or other automated means to access or collect data" from the Service; the SQL API's own rules sit in a separate Addendum I could not read (not verified). Circumventing credits/rate limits (multiple accounts) is banned. Terms do not address caching/storing results or commercial use of results. Public user content may be forked/copied with credit to the creator. Data is "at your own risk". So automated API use on a paid plan is probably what the Addendum covers, but that needs reading before building on it.
- Fork or write our own: forking public queries is allowed with credit (terms). Saving a query needs an account; running it via API needs a paid plan (Read/Write scope for creating queries by API; exact endpoint not checked). Private queries are paid-only. Whether Dune has decoded pump.fun tables (and their names) is NOT verified: docs.dune.com's Solana pages describe decoded tables generically (`<namespace>_solana.<program>_call_<instruction>`, top-level instructions only, per [IDL tables](https://docs.dune.com/data-catalog/solana/idl-tables)) and do not mention pump.fun. A creates-with-migrated-flag query is plausible from decoded `create` and `migrate` instruction tables (non-migrated = left anti join), but I could not confirm the tables, so treat it as unproven.

## 3. Backfill and coverage cross-check

- Months of graduations: the dashboard's own charts run from 2025-06-25 to 2026-11-08 (fee chart, query 3759856), so the underlying data covers at least 16 months. Per-token history for our fields is not verified.
- Cost: unknown without running. Plausible shape: a one-off month of Analyst ($75, 4,000 credits) or the trial's 2,500 credits for 7 days. Result-fetch cost is by size and falls with fewer columns, so pull only `mint, created_at, migrated_at`. Execution cost scales with compute and is shown only after running.
- Coverage cross-check: yes in principle. Daily graduated and non-graduated counts exist as `daily_graduated_token_count` / `daily_nongrad_token_count` (query 4861426) and monthly `monthly_graduations` (query 4048901); comparing our ~800/day against `daily_graduated_token_count` for 2026-11-09 and 11-10 would test PumpPortal coverage. The dashboard only exposes these as chart data on the page (viewable free, no API). A free manual check by reading the dashboard in a browser is enough for a one-off.
- Dune cannot fix the 8% metadata coverage: it holds on-chain data, and token name/symbol/uri come from the create event only if its decoded table exposes them (not verified). The description/website/X fields live in off-chain metadata JSON, which still needs our own fetches (and the `ipfs.io` 429 problem in `new-phase-gap-2026-11-11.md`).

## 5. What argus needs

- Egress: `api.dune.com` (HTTPS, 443). The brain and ingest run on the host, not in the Build container, so ADR 0005's proxy allowlist (`api.anthropic.com`, `registry.npmjs.org`) is not affected; Build containers must not get it.
- ADR 0002 and its Amendment (`docs/adr/0002-argus-does-not-launch-tokens.md`): read-only, "public RPC and public market APIs, no wallet, no keys, no transaction". Dune is a read-only analytics API, so no conflict with the boundary. But the Amendment says "public ... APIs" and the repo test `packages/core/src/adr-0002.test.ts` bans RPC/trade hosts via `BANNED_HOSTS`; `api.dune.com` is not an RPC host so it would not trip it (I read the test's host list, not every line). A paid API key is not "keyless public": ADR 0008 set the precedent of recording access, rate limit, terms and "no secret added to `.env`", so a new ADR or an ADR 0002 note on a paid source would be the consistent move. Not decided here.
- Secrets: the repo keeps keys in git-ignored `.env` or the OS secret store, never in the repo, agents never print them (`docs/architecture.md` section "Keys never in the repo", line 332); Helius uses `HELIUS_API_KEY` there. A `DUNE_API_KEY` would follow that and be kept out of every child process and container env (allowlist in `containerEnv`, `docs/architecture.md` line 173).
- Conflicts with ADRs: none found with 0002, 0005, 0008. Would add a paid dependency to a Study that data-sources.md meant to run at about $5-25 a month.

### Query 4124453 "Graduated Tokens" (@adam_tehc, 54 stars)
- Last run 2d ago (took 2m), "Updated 3mo", 512 result rows. Verified.
- Tables (Dune "Data sources" panel): `solana.instruction_calls`, `dex_solana.trades`. Verified. No decoded `pumpdotfun_solana.*` table.
- SQL (seen lines 1-46, 50-102; lines 47-49 not seen): CTE `withdraws` = `account_arguments[3] AS token_address` from `solana.instruction_calls` where executing_account = program, discriminator IN (the two graduation values), last 24 h, tx_success, inner-instruction filter. CTE `token_prices` = `dex_solana.trades` rows (amount_usd >= 1, last 24 h) where bought or sold mint is in `withdraws`, price = amount_usd / amount, `ROW_NUMBER() ... ORDER BY block_time DESC`. `ranked_prices` keeps rn <= 7 (the last 7 trades). `trade_counts` = trade count per token in 24 h. Final: `RANK() OVER (ORDER BY vwap * 1000000000 DESC)`, `market_cap = SUM(price*amount)/SUM(amount) * 1000000000`, `WHERE trade_count >= 100`, `ORDER BY market_cap DESC`.
- Result columns: `rank` (shown "#"), `asset_with_chart` (shown "Token", HTML link to fomo.family), `token_address_with_chart` (shown "Contract Address", HTML link), `asset` ("Token"), `vwap_token_price`, `market_cap`, `trade_count`, `token_address` (page showed Token, Contract Address, Token, Market Cap, token_address; vwap and trade_count columns not displayed in the table view I read).
- Sample rows (rank, symbol, mint, market_cap): 1 USPR FQTnKFsQVtwky2LZ1iiQ4fRj5MgCMYN8ySJM1Mdjpump $551,844,959; 2 UDTF 974TXXEeRcmiyYfh7RofWYy3zuW8wKhnCXRVqS6Spump $373,872,929; 3 USDP e42WciTae2TsQMfTcoDPmkAWPm4DoPBGEL1ZPKdpump $175,039,787. (Market caps are implausible, e.g. $551M for an unknown ticker; likely mis-priced thin trades or fake-price artefacts. Do not trust.)
- What it really returns: tokens that had a graduation instruction in the last 24 h AND >= 100 DEX trades, ranked by an estimated market cap (price from last 7 trades x 1e9 supply). It is a 24 h trending list, NOT a history of graduated tokens. No create time, no graduation timestamp column. Not usable for the Study.

### Query 4861426 "Daily Tokens Created" (@adam_tehc, forked from @adam_tehc/Tokens Created)
- Last run 2d ago (1m), 365 rows. Verified.
- Tables: `tokens_solana.transfers`, `solana.instruction_calls`. Verified.
- SQL (seen lines 1-47 approx, 29-80; lines 14-28 partly, 81-85 not seen): CTE `pumpdotfun_tokens` = `MIN(block_time)` per `token_mint_address` from `tokens_solana.transfers` (action 'mint', outer account = program, last 365 days). `graduated_tokens` = `COUNT(DISTINCT token_address)` per day from `solana.instruction_calls` using the three discriminators above, split by slot 266793916 / dates 2025-03-19/20/21 (old vs new program version), with `tx_success` and an inner-instruction filter. `daily_tokens` counts per day; `final_data` LEFT JOINs graduated; non-grad = created - graduated; final SELECT adds cumulative sums with window functions.
- Columns: `date_time, platform, daily_token_count, daily_graduated_token_count, daily_nongrad_token_count, cumulative_token_count, cumulative_nongrad_token_count`.
- Sample rows: 2026-11-08 Pumpdotfun 35077 created / 785 graduated / 34292 nongrad (cum 10951021 / 10763461); 2026-11-07 38465 / 865 / 37600; 2026-11-06 44760 / 746 / 44014. 2026-11-09 row is partial (7393 / 333), the run predates the end of that day.
- What it really returns: per-day counts only, one platform, daily grain; graduated on day D is counted by graduation date, not by creation cohort, so it is not a per-token join. Useful as a cross-check: creates 35k-49k/day, graduations 750-1,100/day (Nov 2026), vs our ~13k creates/day seen and ~800/day migrations. Our graduation count agrees with Dune's; our create count (~13k) is far below Dune's 35-45k/day, so ingest sees only about a third of creates (not verified why; check dedupe/window).

### Answer to the open question
No query on these three pages exposes a decoded pump.fun table (`pumpdotfun_solana.*`) or a per-token (create time, graduation time) pair. All three read the generic tables `solana.instruction_calls`, `tokens_solana.transfers`, `dex_solana.trades` and identify pump.fun by program id and instruction discriminator. A per-token create+graduation table would have to be built by joining `tokens_solana.transfers` (mint, MIN(block_time) = create) with `solana.instruction_calls` (graduation discriminators, `account_arguments[3]`, block_time) on the mint. Query 4861426 already contains both halves but aggregates them to daily counts before joining. Verified: the three pages' table lists. Not verified: whether Dune has a decoded `pumpdotfun_solana` namespace elsewhere (not on these pages), and the discriminator-to-instruction names (inferred: graduation = the migrate/withdraw instruction, `0xb712469c946da122` = old withdraw).
