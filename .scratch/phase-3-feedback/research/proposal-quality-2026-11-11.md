# Proposal quality: feed-viewer Techs, missing rationale (2026-11-11, read-only)

## 1. Sizing (60 `new` Proposals, ids 70-129, read from tech_one_liner by hand)
- Pure fetch/static-and-display (feed, timeline, countdown, schedule, dashboard, gauge, explainer): about 38.
  Examples: 117 Rail Watch Ledger (RSS into timeline), 97 Questionable Tag (injury RSS board), 82 Sea Hawk Sunday (scoreboard dashboard). Also 94, 95, 119, 120, 122, 129, 100 (countdown + feed).
- Has some interaction (calculator, quiz, poll, drag bracket, audio, lookup): about 22.
  Examples: 102 Muse Cost Meter (token-cost calculator), 124 Seed Sheet (drag bracket + permalink), 77 Mouthpiece Lab (sliders + Web Audio).
- Caveat: "interaction" here is mostly a calculator or poll. None has a hook specific to a token community; none is derived from a migrated pump.fun token. So ~38 are worthless to the Operator, and the other ~22 are only slightly better. 129 Proposals exist in total, all with narrative_id and score_id set.

## 2. What the prompts say about Tech value
- Propose skill: `.claude/skills/propose/SKILL.md:16` "one web app on Cloudflare Workers ... build in 1 to 4 hours ... Public, unauthenticated data only. No on-chain programs, wallets that sign, bots, ... paid APIs or accounts. If the Narrative offers no such Tech, propose the closest buildable one rather than a bigger idea." This pushes toward the smallest thing, which is a public-data viewer. No sentence asks for value, interaction, a reason a visitor returns, or a link to a working case.
- Propose prompt: `packages/core/src/propose.ts:124` tech is only "the web app that rides the Narrative" (<=200 chars). Prompt inputs are only Signals + Score + judge rationale (`propose.ts:137-143`); no Case data.
- Judge skill: `.claude/skills/judge/SKILL.md:17` "Buildability is a hard gate ... could credibly be built ... unattended"; it rewards easy, which is exactly a feed viewer. Rubric (`rubric_versions` v1 in DB, `packages/core/src/rubric.ts`): buildability = "Whether a small web app can credibly be built and deployed from it unattended (hard gate)"; hook = "How easily the idea is explained and shared in one line". Nothing scores whether the Tech does something useful. Judge sees the Narrative only, not the Tech (Tech is invented later in propose), so no stage ever judges Tech value.
- ADR 0003 (`docs/adr/0003-one-build-archetype-via-template-repo.md:3`) fixes the archetype to a Workers web app; it is the right constraint, but it is the only Tech rule.
- GLOSSARY.md:19-20 defines Tech as "the new technology (product) that could be built to ride a Narrative"; no value test.

Shown on `apps/warroom/app/pages/proposals/[id].vue`: narrative summary, tech, why now, description (l.136-139); a link to the Narrative (l.144-148; Signals live on `narratives/[id].vue:67`, not on the Proposal page); evidence links (l.154); total score pill (l.133), per-dimension ScoreBars + judge rationale + Rubric version (l.237-243); collision checks (l.247); brain runs (l.263-275, no content).

## 5. Recommendation (quickest, fits Phase 3)
Do not build the Phase 3 loop twice: ticket 09's mechanism (a delimited, sanitised block rendered next to the Rubric, versioned) is the right vehicle. Add three small tickets that reuse it.
A. Tech-value rule in propose + judge text and rationale field. Model: sonnet / medium. Edit `propose/SKILL.md` and `propose.ts` prompt: Tech must have an interaction or a hook a visitor returns for (input that changes output, a game, a calculator, a tool, a mechanic), and must not be "fetch a feed/API and display it"; require a new output key `reason` (one line: which Signal/Case pattern, why this Tech). Also add a judge dimension or sentence scoring "does the Tech do more than display data" via the existing Rubric editor (new Rubric version, not a code change). Needs worker restart; merge between runs. Validator: add a cheap code check refusing tech matching feed/RSS/tracker/dashboard/"live feed" without an interaction word, with the repair retry from ticket 21 (do not loosen it).
B. Store and show the rationale. Model: sonnet / medium. Add `proposals.reason` (+ optional `tech_kind`) columns, persist the propose `reason`, and on `proposals/[id].vue` add a "Why this Proposal" panel: Signals used (top N), judge per-dimension scores with the weakest/strongest marked, judge rationale, propose reason, Rubric version. Later the same panel gets Playbook version and cited Cases (09's column).
C. Interim grounding from the existing Study table. Model: sonnet / high. Render a read-only block of N recent migrated Study tokens (name, symbol, description, site title, empty_shell false) into the propose prompt as untrusted data, labelled "examples of tokens that migrated, not a recommendation"; hard-cap and sanitise like Signals. This is a cheap precursor of ticket 09 using the same renderer; when 03/04/07/08 land, replace its source with approved lessons and chain-verified organic migrators. Caveats to state in the ticket: migrated_at is PumpPortal receipt time and unfiltered for bots (spec section 7), so it is a hint, not a lesson; the Operator should decide whether to accept that until 04 exists.
Independently: ask the Operator to decide the ADR 0002 test change (allow the Helius host only in a Study module) now, since it gates 03 -> 04 -> 07 -> 08 -> 09, the real grounding path.
