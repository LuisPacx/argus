# 01: Rising clips for one topic, shown in the War Room
**Model:** sonnet / high. This is the X-session code: a new Playwright child process on the logged-in account, third-party text end to end, a lock shared with other X jobs, and stop rules that protect the account. Not opus: the design is settled in the spec and ADR 0009's 2026-11-19 amendment.

**What to build:** the smallest slice that is useful alone. For one topic given by configuration, the worker scans X for rising video clips every 30 minutes, stores each post with its counts at each reading, and a new War Room page `/moments` lists the clips that are rising fast (views an hour), newest reading first. The Operator opens the page and sees what is moving in the topic without running a manual scan. Nothing else yet: no grouping, no model, no coin side (tickets 02 to 04).

**Status:** ready-for-agent

**Blocked by:** none
ADR 0009 is amended in the same change set as this ticket's spec; the Operator's go-ahead of 2026-11-19 covers it. The Study's X capture, Phase 3 ticket 06, is not built; this ticket moves the Chrome-directory lock and the stop state into shared modules so that job can use them later (ticket 08 adds the wrapper).

## Evidence and design (read before building)

- The method it replaces: `.scratch/research/gta6-post-release.md`, "Scan 2026-11-19 15:20 UTC" group B (`filter:videos`, `min_faves:500`, Top and Latest, views an hour = views / hours since posting, "rising only" at 50K an hour). Group A and the qualifying bars are ticket 02.
- The X page: `packages/core/scripts/x-capture-spike.mjs` reads `article[data-testid="tweet"]`, which X no longer serves in search results. Posts are bare `article` elements; counts are in the action row's aria-label ("44 replies, 39 reposts, 185 likes, 4 bookmarks, 18856 views"); there is no time element in search results, so the time comes from the status ID (the post URL's last number): `(id >> 22) + 1288834974657` ms. Check against the notes: status 2123280111864811617 is 2026-11-19 05:00:01 UTC; 2123384751901778317 is 11:55:50 UTC. Views are sometimes not shown.
- Reuse `packages/core/src/x-capture/detect.mjs` (`classify`, `statusOf`, `STOP`, `captureAll`) as is. Its signals were written from X's known behaviour and never seen live (`.scratch/phase-3-feedback/issues/05-outcome.md`); this ticket is the first long run, so a STOP stops the day.
- Spend: no Claude, no Brain. The scan is a plain child process like the Study's planned capture.
- Topic by configuration for now: `ARGUS_MOMENT_TOPIC` is one JSON object `{ "label": "GTA VI", "startsAt": "2026-11-19T05:00:00Z", "spellings": ["GTA VI", "GTA 6", "GTA6"] }`, validated; ticket 05 replaces it with a table. Switch `ARGUS_MOMENTS=1` (off by default, like `ARGUS_MEME_IDEAS`).

## Build

1. `packages/core/src/x-capture/lock.mjs`: `lockHolder(dir)` and the directory-safety checks moved out of the spike (mode 700, outside the repository, one process per directory); the spike imports it. Behaviour unchanged.
2. `packages/core/src/moments/`: `status-id.ts` (time from a status ID), `counts.ts` (aria-label to `{ replies, reposts, likes, bookmarks, views }` with `null` for a figure not shown, never 0; also "1.2K" and "3M" forms), `rate.ts` (views an hour since posting; recent rate between two readings; the rate floor of 30 minutes and 20,000 views; a post with no views never rates), `query.ts` (the query builder, below), `config.ts` (every number in one file, with its source).
3. `packages/core/src/x-capture/posts.mjs`: an in-page collector that returns plain facts per bare `article` (status link, handle, innerText, aria-label, has video, quoted-status link if the DOM carries one) and a pure parser from facts to posts. A page where no article is found is the status `selectors_found_nothing`, a different thing from `ok` with zero posts, and it stops the scan.
4. `packages/core/scripts/x-search-scan.mjs`: the child process. It takes a JSON plan on stdin (a list of `{ id, url }`), opens the dedicated profile (`ARGUS_CHROME_DIR`) headless as the spike does, loads each URL serially with 9 to 22 s jitter and at most 3 mouse-wheel scrolls, and prints one JSON line per page (posts, status, signals). It refuses any URL that is not `https://x.com/search?q=...&f=top|live` or `https://x.com/<handle>/status/<id>`, exits 3 when the directory is locked, and stops at the first STOP signal with no retry. It uses `goto`, wheel scrolls and reads only.
5. `query.ts`: the group B query for the topic, `(<spelling> OR <spelling>) filter:videos min_faves:500 since:<startsAt as YYYY-MM-DD_HH:MM:SS_UTC>`, once for `f=top` and once for `f=live`. Words are limited to letters, digits, spaces, quotes, `#`, `$`, cut to 40 characters each; the operators are literals in code. A spelling that cleans to empty is dropped; no spelling left is a refusal.
6. Store (`packages/core/src/moments/store.ts`, tables created idempotently in the worker's database): `moment_scans` (time, topic, status, loads, signals, reason), `moment_posts` (status ID, handle, text cut to 600 and flattened, posted at, has video, first seen), `moment_post_readings` (status ID, scan, seen at, and the five counts, nullable; append only). The War Room's Datastore view is read-only for all three.
7. Worker step in `apps/worker/src/main.ts`: when `ARGUS_MOMENTS=1`, one scan every `ARGUS_MOMENT_INTERVAL_MIN` minutes (default 30, minimum 15), re-entrant like the other jobs, a dry run spawns nothing. Caps in code: 8 loads a scan, and a daily load cap of 100 by default (`ARGUS_MOMENT_LOADS_PER_DAY` can only lower it; the code ceiling is 300). A locked directory records "skipped: browser busy" and tries again at the next interval.
7a. **The shared stop state, in this ticket so live reading never ships without it** (`packages/core/src/x-session/state.ts`, table `x_session_state`, one row: `status` `ok|stopped`, `reason`, `stopped_at`, `resume_at`, `strikes`, `probe_due`). A STOP signal (`login_wall`, `challenge`, `locked`, `own_suspended`, `rate_limited`) sets `stopped` until 00:00 UTC and sends one Telegram message through the existing queue; `not_found` and `target_suspended` pages do not. The state is the account's, not the scanner's: any X job reads it first and loads nothing while it is `stopped`, so the Study's capture (later) pauses with the scanner and the reverse. The next UTC day the first X job makes exactly one **probe load: the topic's own search URL from the allowed list (never a profile page, so no extra allowed address)**, counted in the day's loads; a clean probe clears the state. A second STOP within 7 days sets `stopped` with no `resume_at` until the Operator presses Resume. Resume is `POST /api/x-session/resume`, one request row (insert only), refused unless `status = stopped`, every press recorded; the worker clears the state on its next tick. The Moments page shows the state (ok, stopped with the signal and time, probe due) and the Resume button only when stopped.
8. War Room: `GET /api/moments` (read only; the topic, the scanner state and last good scan time, and the rising posts) and the page `/moments`: one row per rising post with a link to the post (only for an `https://x.com/<handle>/status/<id>` address through `safeHttpUrl`), handle, text clamped, views, likes, views an hour since posting, recent rate where there is an earlier reading, age, readings count; empty state says why (off, no scan yet, busy, stopped for the day with the reason, nothing rising). A nav link. Text only.

## Acceptance criteria

- [ ] **Status ID and counts** (`status-id.test.ts`, `counts.test.ts`): 2123280111864811617 reads as 2026-11-19T05:00:01Z and 2123384751901778317 as 11:55:50Z; a non-numeric or too-short ID is refused; the real aria-label above parses to 44, 39, 185, 4, 18856; a label with no views gives `views: null`, not 0; "1.2K likes" and "3M views" parse; text that is not a label gives all nulls.
- [ ] **Rate** (`rate.test.ts`): 120,000 views on a post 2 h old is 60,000 an hour and rising; 15,000 views on a post 10 minutes old does not rate (age and views floors); a post 29 minutes old does not rate; null views never rate; FelpsCrypto's numbers (148K views at 13:55, 638K at 15:10; `gta6-post-release.md`) are not rising by the average at 13:55 (about 41K an hour) and are rising by the recent rate at 15:10 (about 390K an hour).
- [ ] **Parser on real pages** (`posts.test.ts`, slow tier if it needs a browser: add it to `SLOW_TESTS` in `vitest.tiers.mjs`): two saved real search pages (a Top and a Latest page for a `filter:videos` query, read with the spike's method, read-only, lock free) are parsed from bare `article` elements into posts with handle, status ID, time from the ID and counts; a promoted post or an article with no status link is skipped; a page with no articles gives `selectors_found_nothing`.
- [ ] **Fixtures are safe** (`fixtures.test.ts`): the saved pages have the account's nav, account switcher and every `<script>` removed, hold no handle of the Argus account, no cookie name (`auth_token`, `ct0`, `twid`); the scrub is a script, and the test runs it over the committed fixtures and finds nothing left to change. Raw unscrubbed pages are written 0600 under a 700 directory outside the repository and never committed.
- [ ] **Query builder** (`query.test.ts`): a hostile topic (`GTA VI from:someone -filter:links min_faves:0 "x" OR (y)`, 10,000 characters, control characters, a spelling that is only operators) produces queries with no operator other than the three literals, no `from:`, no `-`, no parentheses beyond the one around the OR list, and every word cut; an empty topic is refused; `since:` is formatted `2026-11-19_05:00:00_UTC`.
- [ ] **Child process** (`x-search-scan.test.ts`, fake page facts and a fake lock, no real Chrome): a URL outside the two allowed shapes is refused before any load; a held lock exits 3 with no load; a login wall, a challenge, a lock page, a suspension and rate-limit text each stop at that page with no further load and no retry (the spike's `detect` signals, here with the scanner's loop); jitter and the 3-scroll limit hold.
- [ ] **Read-only** (`read-only.test.ts`): the scanner script and the collector contain none of `.click(`, `.fill(`, `.type(`, `.press(`, `keyboard`, `.check(`, `dispatchEvent`, and open no URL but `goto` targets; the test greps them and fails on any.
- [ ] **Store** (`store.test.ts`, real Datastore on a temp dir via `testing/temp.ts`): readings are append only and a repeated scan id adds nothing; text is cut and flattened and `<`/`>` markup is removed (the existing untrusted-text helper); an old database without the tables opens and gets them; the War Room's view cannot insert (type test, as for `enqueueCommand`).
- [ ] **Stop state** (`x-session/state.test.ts`, fake clock): each of the five STOP signals sets `stopped` until 00:00 UTC and sends one message; `not_found` and `target_suspended` do not; while `stopped` any X job loads nothing (tested with the scanner and with a stand-in "study" job); the next UTC day allows exactly one probe load, which is the topic's search URL and not a profile page (asserted against the allowlist), and no more until it is clean; a clean probe clears the state; a second STOP within 7 days leaves `stopped` with no resume time; a STOP after 8 days is a first one again.
- [ ] **Resume** (`apps/warroom/server/test/x-session-resume.test.ts`): POST on a `stopped` state writes one request row and the worker clears the state on its next tick; POST when `ok` is refused; a GET of the page and of `/api/moments` writes nothing (tables unchanged before and after); the War Room process writes no scanner table other than the request row.
- [ ] **Worker step** (`moments-job.test.ts`, fake runner): a scan stores posts and readings; locked records "skipped: browser busy" and loads nothing; a STOP signal stops the day (the state above) and the next scheduled scan loads nothing until the probe; the daily cap of 100 is never exceeded across scans (the 13th scan of 8 loads is cut to the loads left); `ARGUS_MOMENT_LOADS_PER_DAY=500` is an error and 50 lowers it; switch off or dry run spawns nothing; two scans never overlap.
- [ ] **API and render** (`apps/warroom/server/test/moments.test.ts`, `moments-render.test.ts`): GET returns only the listed fields; a hostile post text (`<img src=x onerror=1>`, newlines, 100,000 characters) renders as one clamped line of escaped text; a stored `javascript:` or non-x.com link is never an anchor; the empty states show, and the Resume button shows only when stopped; no `v-html` in any new component (the repo's grep test).
- [ ] **Browser, seeded** (`pnpm page:check --seed /moments`; add a `{moment}` seed with a rising post, a hostile one and each scanner state; say in the box that the run was seeded; never the user's Chrome): exit 0, no console, page or request errors, no horizontal overflow at 390 or 1240 px, screenshots read; keyboard: `--keys "focus=[data-test=x-resume]"` focuses the Resume button without pressing it (the script blocks non-GET).
- [ ] **Live read, once** (not a test; the Operator or a worker with the Argus Chrome lock free, GET only on x.com, Chrome closed afterwards): one real scan for the GTA VI topic, 8 loads or fewer; paste the scan row, the post count and the three highest rates in Comments. A scan that hits a wall is a valid result: record the signal and stop. Leave the box open until it is run.
- [ ] Type-check (`tsc --noEmit --checkers 1`), `pnpm lint` and the full `pnpm check` pass, run once before the commit.

## Constraints

- Follow `docs/agents/worker-rules.md` and `CODING_STANDARDS.md`. No RegExp built from a post, a topic or a query. The worker never fetches a URL found in a post. Nothing here posts, likes, follows or messages.
- The scanner is not a Source: no Signals, no `source-class.ts` entry, no clustering (ADR 0009, ADR 0011).
- Commit subject `Moment scanner ticket 01: rising clips for one topic`, body ends with `Ticket: .scratch/moment-scanner/issues/01-rising-clips-for-one-topic.md` before the trailers. No `Closes #N`.
