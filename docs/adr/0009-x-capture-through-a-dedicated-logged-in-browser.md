# X capture through a dedicated logged-in browser

Status: accepted (Phase 3 spec, 2026-11-07; Operator decisions Q9, Q13, Q14). Replaces the architecture's "X returns later through the official API" for the Study. Not yet built.

The Phase 3 Study (`.scratch/phase-3-feedback/spec.md`) needs the X profile and recent posts of up to about 200 pump.fun tokens a day, captured at a fixed early age and stored as frozen Snapshots. Argus captures them with a Playwright script that opens a dedicated Chrome user-data directory (default `~/.local/share/argus/chrome`, created by `.scratch/phase-3-feedback/setup-argus-browser.sh`) where a new, Argus-only X account is logged in. The script saves text and raw artefacts; Claude only reads the saved Snapshots, never drives the browser. The Claude in Chrome extension is installed in the same directory for manual checks by the Operator. The Operator accepted the Terms of Service and account-lock risk below.

## Considered Options

- **Official X API, pay-per-use.** The only route X's terms allow. At about 100 studied tokens a day with 10 posts and 10 mentions each it costs roughly $330 to $630 a month (posts $0.005, users $0.010, per resource returned); even a matched subset of about 20 tokens a day is $66 to $126. That alone exceeds the $100/month Study budget. Rejected on cost; it remains the compliant path if the budget changes, behind the same capture seam.
- **Third-party X data APIs (twitterapi.io and similar).** About $20 a month at this scale, but they rely on scraping X, which X's terms forbid, and can vanish, be blocked or change price without notice. The ToS exposure is the same as the browser's and the dependency is worse. Rejected.
- **Claude in Chrome per token (Claude drives the browser in `claude -p`).** Spends a Claude run on every capture, which breaks "capture broad with no Claude, analyse narrow" (Q16); `claude -p --chrome` is not documented for unattended use, browser selection and site permissions can block runs, and the extension connection drops when its service worker idles. Kept for manual checks only.
- **A Playwright script on a normal profile or in a throwaway context.** Chrome 136 and later ignore remote-debugging switches on the default data directory, and a throwaway context has no login. Hence a dedicated, non-default directory and a dedicated account.

## Consequences

- **Terms of Service.** X's terms forbid access other than through its published interfaces and forbid scraping without written permission; browser automation of x.com is on the wrong side of that. The Operator knowingly accepted this for a dedicated account. The exposure is the account (rate limits, challenge, lock or suspension), not a personal one, and possibly the IP.
- **Containment of the risk.** A new account used only by Argus, with an authenticator-app second factor; about 200 captures a day, serial and paced; the script stops for the day, notifies the Operator and does not retry on a login wall, challenge or lock signal; it never posts, likes, follows or messages (architecture invariant 6, no fake organic interest). X data is optional: with it off, the Study falls back to website, metadata and chain data.
- **Secrets.** The directory holds the account's session cookies. It lives outside the repository, mode 700, and outside any backup that is shared. The wizard stores no password, phone, email or 2FA seed.
- **Operations.** One browser process may own the directory, so a manual "Argus Chrome" session and a capture run cannot overlap; the script checks and refuses. Whether X treats headless Chrome differently is unproven; a spike decides headless against headed (virtual display) before the daily job is trusted.
- **Untrusted input.** Captured X text is written by third parties; it reaches Claude only as delimited data with no tools, like Signals.
- **Not the helios scraper.** Architecture section 11 lists the helios X cookie scraper and burner-account machinery as not ported. This is a different, deliberately smaller thing (one account, read-only, capped), and that line should be reworded when the architecture document is next edited.
- **Seam.** Capture sits behind one function that returns the Snapshot's X fields, so the official API or a vendor can replace the browser without changing the Study.

## Amendment 2026-11-19: the moment scanner may search and scroll X (moment scanner spec; the Operator approved amending this ADR for it on 2026-11-19 and accepted the shared account, the first-week 100 loads a day and the ramp to 300; the other numbers are proposed defaults he may change)

This ADR let the browser do one thing: open a profile or a post list and read it, for the Study's Snapshots. The moment scanner (`.scratch/moment-scanner/spec.md`) needs a second use of the same account and browser: **search X and scroll the results**, on a schedule, for Watched topics, and re-read single posts, to count views and likes and find posts that are spreading. Nothing else about the decision changes: one logged-in account used only by argus, read-only, no Claude driving the browser, text saved as untrusted data, X data optional.

What is now allowed, and only this:

- **Pages.** `https://x.com/search?q=<query>&f=top|live` and `https://x.com/<handle>/status/<id>`, opened by URL (`page.goto`), plus mouse-wheel scrolls and DOM reads. The Top and Latest tabs are chosen by the `f` parameter, never by a click. No click, type, post, like, follow, repost, bookmark, reply, message or profile edit; no other URL (no home timeline, lists, notifications, DMs).
- **Queries are built by code.** The words come from a Watched topic (a Meta's label and its launch-theme labels, or the Operator's text), limited to letters, digits, spaces, quotes, `#` and `$` and cut to a length. The operators (`since:`, `min_faves:`, `filter:videos`, `OR`) come from a fixed list. A topic's text can never add an operator, a `from:` or a negation: it is untrusted (token names are written by their creators), and a bad query is a logged skip, not a search.
- **Load limits, in code, lowerable and never raised by configuration (architecture invariant 3):** per scan, per hour, per day, and per page in scrolls. Proposed defaults: 8 loads a scan, 24 an hour, 300 a day for the scanner, 3 scrolls a page, 9 to 22 seconds of jitter between loads (the spike's pacing). The scanner starts at 100 loads a day for the first week and reaches 300 only after a week with no stop signal (the Operator's decision of 2026-11-19). These are the scanner's own caps and are added to the Study's 200 captures a day, so the account may see about 500 loads a day at the ceiling, 2.5 times the volume this ADR sized and about 40 times the 12 loads the spike tried. That is a larger Terms-of-Service and lock exposure than the one the Operator accepted above, and approving this amendment accepts it for scanning. The account is shared with the Study: a lock stops both. The Operator chose to share the account (2026-11-19); a second account and directory for the scanner would separate the risk and stays an option if a wall appears.
- **One owner of the browser directory.** The scanner, the Study's capture and the Operator's manual Argus Chrome session take one lock between them (the spike's `SingletonLock` check, moved into a shared module). A job that finds the lock held skips its turn and says so; it does not queue behind a long job or retry in a loop.
- **Stop rules are the Study's.** The first login wall, challenge, lock, suspension or rate-limit text stops the scanner for the rest of the day with no retry and notifies the Operator; the next day starts with one probe load, which is a search page from the allowed list above (the topic's own search URL), never a profile page, so the probe needs no extra allowed address. A second wall within 7 days stops the jobs until the Operator re-logs in if needed and presses Resume in the War Room (one request row; the worker clears the state). A stop by either job pauses both X jobs, because the account is shared. The state, the probe, the second-wall stop and Resume ship with the scanner's first live scan.
- **No Claude in the browser.** The scan is a plain Playwright child process. The model sees only the saved post text, in a fenced block of untrusted text with no tools, as before.
- **Page reading.** X search results no longer carry `data-testid="tweet"`: posts are read from bare `article` elements, counts from the action row's aria-label, and the post time is decoded from the status ID. A page where the selectors find nothing is its own status ("selectors found nothing"), not an empty success, and stops the scan.
- **What is stored.** Post text (cut), author handle, status ID and time, counts at each reading, and links, in the worker's database; raw HTML and screenshots only on a failure, written 0600 under a 700 directory outside the repository, and never committed (a saved page holds the account's own nav and handle). Saved real pages used as test fixtures are scrubbed of that handle and checked by a test.

What this does not change: the scanner is not a Source and produces no Signals (the architecture's "No X as a Source" line, ADR 0011), the Study's own captures keep their cap of about 200 a day, X data stays optional with a switch (`ARGUS_MOMENTS`, off by default), and argus still never posts, likes, follows or messages (architecture invariant 6) or launches (ADR 0002). The official API remains the compliant path and stays behind the same seam if the budget or the risk changes; whether it can do this search, and at what price, was not checked for this amendment.

## Amendment 2026-11-19 (trend radar): a Trend is a third origin of topic text

A Watched topic can also come from a Trend (trend radar tickets 06 and 13, ADR 0016): a third origin of topic text after a Meta and the Operator, built from cleaned third-party text (a feed term or a model-written phrase) under the same limits (the scanner's one cleaner, the fixed operator list, the same load caps, ramp, lock and stop rules). Nothing else in this ADR changes.

## Amendment 2026-11-20 (human researcher ticket 05, ADR 0017): an Operator's research request reads X once

A topic the Operator types on the Research page and presses Research for is a fourth origin of topic text. The worker's research step reads X for it through the same child process, the same profile and the same session gate as the scanner (the scanner's switch is not needed: the press is the Operator's trigger), and nothing else about this ADR changes: the two search pages of the allowed shape only (Top and Latest, `f=top|live`, built by code from the scanner's one cleaner plus the fixed `since:` operator), no click, no profile page, one owner of the browser directory (a held lock is a note in the brief and a skip, never a wait), the same STOP rules (a stop by this read pauses the scanner and the Study, and the Operator is told), and read-only. Its loads count in the shared daily cap (the scanner's `moment_scans` table, under the label `research: <topic>`, which the scanner's own last-scan reading leaves out) and have their own caps in code on top: 2 loads a request and 20 a day of research's own. The posts reach the model only as fenced untrusted text; the model gets no browser and no X tool. X data stays optional: a request with no X read still gets its brief, and says why in it.
